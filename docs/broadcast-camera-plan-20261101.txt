统一导播与遮挡处理方案 v1（2026-11-01）

目的
让导播通过同一相机控制器选择人物、构图和可见性策略。正交相机作为可选镜头加入现有系统，保留 Java 真实客户端、网页渲染、第一人称、第三人称、无人机、俯视和地下城视角。
本文件是整体设计及能力审计，不能当作功能均已部署的证明。

一、把三个概念分开
画面来源：Java 真实客户端；基于本人真实连接/接收场景数据的网页渲染。
投影方式：透视；正交。
构图与遮挡策略：第一人称、近肩、前后第三人称、无人机跟随、总览、俯视；物理遮挡、人物轮廓、局部淡出、当前房间剖切。
例如，“网页＋透视＋房间剖切”和“Java＋正交＋高位总览”是两个合法的候选组合。后端不支持的组合必须 unavailable，不能悄悄改成另一种画面。
当前原生无人机的高角度总览仍是透视构图；高角度不自动等于正交。

二、三类遮挡处理分别做什么
自动检测：使用人物头部、胸口、双侧和脚部等采样点，沿真实相机方向检测接收/加载的方块几何；结合画面占比、屋顶、近裁面和当前活动判断镜头是否可用。它只负责发现问题，检测本身不会让墙消失。
轮廓：对被挡住的主体绘制柔和轮廓，帮助观众定位。轮廓看不清完整表情、动作及手中操作，不应成为人物长期藏在墙后的借口。
局部淡出：仅淡化相机与目标之间的树叶、立柱、屋顶或墙体片段；保留边缘和结构提示。优先屏幕门/抖动式覆盖，避免对大量地形直接启用传统 alpha 混合造成排序错误。
局部剖切：在已确认的当前房间/楼层及必要视线走廊内，切开顶棚或前景墙；保留承重地板、当前层家具和周边地形。剖切边界需要合理的原材质截面，不让场景变成空壳。
所有处理只改变观战显示，不能删除服务器方块、移动游戏主体或把剖切后的观战画面当成游戏 Agent 已获得的感知事实。

三、按场景选择策略
露天活动：第三人称/无人机跟随；建设和村庄展示可以正交全景。少量遮挡先小幅改角度或升高，短暂遮挡可补轮廓，不切开整座山。
狭窄矿道：优先真实第一人称，其次带碰撞裁距的近肩跟随。保留挖掘方向、准星与目标方块关系；不维持拉远的正交镜头。
宽阔洞室/地下城：第三人称或战术构图，配合当前连通空间的局部剖切；保留地板、落差、门洞、掩体和当前空间内的敌人。
竖井/梯子/电梯/跌落/飞行：临时进入过渡构图。仅凭 Y 值不能判定所在楼层；无支撑地面不能凭空建立房间切面。
多层建筑：按人物实际支撑面和房间拓扑建立当前楼层，隐藏当前区域的上方遮挡层，保留当前层地板及下方结构。楼层高度不可固定为三格或四格。
楼梯/坡道：识别楼层之间的连接边，使用楼层归属保持时间；抵达新平台并稳定后再切层，不能每上一个台阶就切一次镜头。
中庭/挑空/夹层：可见性不能只用一个全局高度平面。上层走廊、屋顶、下层地面和房间归属需要分别表达。仍可切换物理透视镜头保留垂直空间关系。
隔墙相邻洞穴：不因“相同高度”就一起揭开。当前房间、门口和邻室需要区分；未知区块不推测为洞穴或空气。
制作台/容器/对话：尽量保持稳定近景，必要时展示真实目标 GUI；切镜不抢游戏 Agent 控制权，也不把观战者自己的库存当作目标库存。
不同角色在不同楼层：主镜头明确跟随一个角色；第二路画面仅在有匹配来源、明确合成后端和资源预算时启用，不能宣称单个 Java 窗口已经具备多路渲染。

四、统一导播的分工
游戏 World/核心提供真实主体 UUID、维度、连接/世界版本、位置、地形、实际活动与回执证据。
共享可视化层提供相机、加载几何、碰撞/遮挡检测、当前房间/楼层状态、可用镜头和显示操作终态。
导播宿主提供模型、人格、节奏与节目目标。模型低频选择“看谁、画面来源、镜头、保持多久、原因”；不逐帧算 yaw/pitch，不在核心隐藏第二个模型循环。
快速本地控制负责跟随、碰撞裁距、遮挡应对和平滑。建议从 5–10Hz 质量检测、按需重建房间、模型正常每 15–30 秒或显著事件一次开始实测，再按资源数据调整。
现有规则选择器保留为模型不可用时的显式回退，但必须作为同一控制器的提案来源，不能继续与 LLM 并排抢写原生请求文件。
主播解说与游戏角色语音继续走既有演出/TTS及发言队列，不在相机组件中另开语音通道。

五、共存与控制协议
只有一个协调器持有当前播出相机的租约。原生 NativeDirector、OrthoCamera、可选自由相机和网页相机均是受调度的执行后端，不能同时修改同一画面的姿态/投影。
同一后端内切构图时保持原目标身份、HUD 与 YSM 动作源；只更改观战相机，不改变主体的游戏视角/动作。
切 Java/网页来源前核对同一目标 UUID、维度、世界/连接版本和资料新鲜度，等待新来源准备好再播出。原模组资源不支持时明确不可用，不用近似皮肤或方块替代。
同类投影的角度/距离变化使用有时长的平滑过渡；正交与透视可先使用明确的切镜。真正的两画面渐变需要额外渲染/合成资源，不能把参数插值冒称为已经实现跨源渐变。
手动锁镜立即阻止新提案，重新启用必须是明确的交还操作。保留最短驻留和切换冷却，避免反复横跳。
操作使用稳定 actionId、控制租约、目标 UUID、世界/连接版本及时效。受理、过渡、已渲染、取消、未知分别记录。RPC 返回不代表已播出，更不代表整轮 Agent 决策完成。
取消等待不等于取消真实操作。适配器必须处理取消确认与旧 ID 的取消记录；停止后迟到的旧模型结果不能再提交，未知操作不能盲目重投。
正常停止可保留当前镜头；后续切镜须有新的明确控制会话。切镜与取消不会重置 Agent 目标、记忆、任务账本或别人的声音。

六、已经存在的源码基础及边界
1. NativeDirector：第一人称、前后第三人称、无人机跟随/高位总览；原生相机碰撞裁距、身份回读与人工交还已有实现。
2. 网页 room-visibility/room-floor-mask：已有当前连通地面、局部屋顶/前景剖切、渐变揭示和地板保护；native-room-visibility 也是浏览器的原生资产渲染路径，不等于 Java 客户端插件。
3. 现有 RoomFloorMask 每个 X/Z 列只记录一个选定高度，并允许有限台阶传播。这不是任意多层建筑的通用楼层图；楼梯回路、同列夹层、中庭与跨层门洞需专项夹具和实际画面验收。
4. OrthoCamera：独立 1.21.1 单机已跑通五种构图；固定位置四角度对比证明换角度可以避开灯柱，但不是自动避挡上线证明。
5. 现有智能选镜是确定性规则；本次尚未启动 LLM 导播，也未改现役单一选择器。
6. Java 的人物轮廓、Sodium/光影兼容的局部淡出、真正房间剖切、跨源画面合成均未通过本次现役验收。Java 不支持时先用物理相机/第一人称；有同身份且完整的网页来源时才提供剖切候选。

七、改进楼层模型的要求
由原始碰撞/形状及接收状态构建有界的三维可站立空间图，不把所有非空气方块当成完整实心立方体。
房间节点、支撑面和高度区间、楼梯/梯子/门/电梯连接边分别记录；同一 X/Z 支持多个高度样本。
自动聚合当前房间/楼层并输出可信度；过渡区保留上一归属，未知或跳跃时不强行切层。不可自动识别时允许人工指定楼层或锁镜。
更新只随相关区块修订、人物跨房间/楼层及相机明显变化触发，不能每帧重扫整栋建筑。
相机可见性、房间揭示和远处实体剔除是三种不同策略，不因某一区域被切开就任意显示所有地下实体。

八、分阶段交付与验收
阶段 A：统一只读能力、相机计划与终态接口。现有视角先接同一协调器，保留人工锁镜和规则回退；LLM 先影子模式记录建议，不抢当前播出。
阶段 B：单个已存在主体的动态切换和平滑；一模一场景验收位置、HUD、YSM动作连续性、GUI与返回原镜头。
阶段 C：露天柱子/树叶遮挡，狭窄矿道、宽阔洞室、隔墙洞穴、楼梯/U形楼梯、三层房屋、中庭、半砖/透明块、飞行/跌落和未知区块夹具。
阶段 D：Java 轮廓与有限前景淡出，按 Sodium/YSM/光影组合逐项验收；完整剖切先复用网页已支持路径，再决定是否移植 Java。支持不足时公开 unavailable 原因。
阶段 E：单一现役观战客户端控制权交接，最后才接实际播出/OBS及跨源合成，并记录最终节目画面。
应测：可见人物比例、镜头穿墙、错误切层、每分钟切换数、手动夺回、取消及停机晚到回调、场景切换时延、CPU/GPU/显存、模型频次与 tokens。每次部署与实际像素验收独立记录。
