# 游戏直播镜头的选择与连接

本文是结合参考资料和本项目接口整理的实施规则。建议数值是待实测的初始值，不是行业标准，也不代表后端已经支持。

## 先选信息，再选运动

镜头应让观众理解地点、行动、双方关系、操作结果或人物的真实反应。先确认主体在做什么和相关物体的位置，再安排构图；不为获得一个镜头去改变游戏 Agent 的行为。

同一个活动可以有多个合理镜头，选择当前最清楚且切换代价最低的一个。静止镜头中人物、动物、作物或水面的运动已能带来生活感，无需额外持续旋转。慢镜头和短镜头的时长服从事件本身与执行器限制。

## 可重复使用的镜头段落

以下是可变的覆盖思路，不是必须按顺序执行的脚本。

| 实际活动 | 优先保证的信息 | 可以采用的镜头组合 |
|---|---|---|
| 抵达新区域 | 人物从哪里来、接下来去哪里 | 开阔关系镜头 → 行进跟随 → 有意义的地标细节 |
| 普通赶路 | 前进方向和沿途环境 | 平视后跟或侧跟；有空间时短暂正面领拍 |
| 种田、制作、钓鱼 | 工具、目标和结果之间的因果 | 稳定中景；真实结果出现时插入细节；随后回到活动范围 |
| 战斗开始 | 主体、敌人、退路 | 关系俯视或稳定过肩；关键命中期间保持可读性 |
| 战斗结束 | 成败和实际后续行为 | 先保留结果，再考虑短推近、低机位或有限环绕 |
| 多人交流 | 谁对谁说话、谁在回应 | 双人/小组镜头；真实反应可见时才取反应镜头 |
| 竣工展示 | 完整结构和尺度 | 稳定全景、有限弧线或拉远；确认整段路径已知 |
| 狭窄矿道 | 挖掘方向和目标方块 | 第一人称或近肩；出矿道后再交代大空间 |

## 连续性

- 为行进、战斗主敌或对话双方建立主要动作轴线，尽量保留切镜前后的左右关系。180° 是帮助理解空间的准则，不是禁止相机经过任何角度；连续运动或重新交代空间的宽镜头可以解释跨轴。
- 相近角度和相近景别的硬切容易产生跳动感。改变构图时要有清楚的信息差；用户要求渐变时按约定叠化，不将长时间双影当成连续性补救。
- 关注点不总是头部。挖掘要看到工具和目标，战斗要看到敌人或攻击方向，对话需要可见双方。用实际身高、姿态和模型边界决定机位。
- 让运动方向前方有空间。以真实行进趋势稳定构图，减少原地转头、扫描和短时网络抖动带来的相机摆动。预测过强时降低前视量。

## 给运动写清起止

有限环绕：确定中心、半径、起始侧、弧长和末机位，再确认整段视线与碰撞余量。建议先评估 30–90° 的弧线；到达结尾后稳定，不无条件接下一圈。

推近/拉远：同时说明目标占画面的变化和需要保留的环境关系。相机平移会改变视差；改 FOV 不等价。正交投影用画面尺度表达，不能套用透视镜头焦距。

横移/领拍：依据主体的真实运动方向及速度维持关系。领拍前要知道相机后方路径，不能只看角色正脸。

升降/俯仰：升降改变机位位置；俯仰改变朝向。展示高塔时二者可以组合，但先确定主要运动，避免同时平移、旋转、变焦和滚转。

快速甩镜、持续手持抖动、荷兰角和眩晕式变焦不作为普通游戏生活直播的默认动作。它们可作为有明确表达目的且后端支持的特殊镜头。

## 切换节奏和质量门

把主体驻留、同主体构图驻留、机械避挡分开。现役原生切人门至少 10 秒，宿主通常保持主体更久；不能为了 2 秒的细节模板绕过这个门。只有后端声明支持独立短构图时，才安排短插入镜头。

候选镜头先排除未知世界、目标身份不符、不可达路径、碰撞或错误楼层，再比较主体可见程度、主体占比、动作可读性、轴线与切换代价。新候选持续更好才切换，并保留最短驻留，避免在等价机位之间来回跳。

挡住人物时先检查是哪类问题：近裁面撞墙、视线被挡、人物太小、所在楼层误判，或数据本身过期。不要用同一种转圈动作解决所有问题。多点射线只是一种几何估计，不等于完整 YSM 网格在最终像素中的可见比例。

## 预览、节目和转场

专业预览/节目分离需要真实存在的画面来源和合成后端。当前单个 Java 观战窗口不能因为计算了候选姿态就宣称候选画面已预渲染；也不能向未配置的 OBS 服务发送命令。

同主体近距离机位变化可平滑插值，但过渡路径也要检测碰撞。跨人物、远距离、换维度时优先在两个已确认画面之间短叠化，避免可见地飞越地图。只有一台原生渲染相机时，可以暂留带“切换中”标识的上一帧，等新视角真正渲染后释放；要有失败和最长等待处理。

相机轨迹插值、两个画面的叠化、物体本身的局部淡出是三个独立功能。切镜不要重复触发 TTS、停止其他角色台词或重播背景音乐。

## 复盘

记录：为何选择、使用了哪些真实事件、实际镜头和目标、可见性问题、切换频率、转场时延及资源成本。评估矿道、跨楼层、多人战斗和对话时要保留真实帧。将用户审美偏好与角色记忆交给宿主保存，按键替换动态事实，不把大量逐帧诊断重发给模型。
